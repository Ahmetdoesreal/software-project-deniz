\begin{abstract}
This paper presents the design, implementation, and validation of a network-based laboratory exam system intended for use in controlled university computer-lab environments. The system follows a client--server architecture: a single authoritative server process running on the local network coordinates exam lifecycle, persistent user state, policy distribution, and submission collection, while one client process per student handles authentication, local monitoring, incident reporting, and final upload. The runtime protocol uses checksum-protected JSON over HTTP and WebSocket, with optional HMAC signing and Fernet encryption for sensitive events. Local UI processes (operator dashboard, student timer window, launcher managers) communicate with their parent command-line processes through a separate loopback-only WebSocket inter-process communication channel, isolating administrative semantics from the student-facing protocol. Monitoring covers process activity, focused-window changes, hardware state, idle behaviour, and on-demand screen replay; an incident-rule engine classifies events as whitelist, warning, or blacklist and applies operator-configured actions. The system also exposes a read-only, privacy-safe projector page for in-room notification display, and supports a temporary authentication-disable workflow with operator approval for CATS and Active Directory edge cases. The current implementation comprises approximately 30{,}000 lines of Python and passes 149 of 151 automated tests, with the two outstanding failures isolated to Windows-path mock fixtures rather than production code paths.
\end{abstract}

\section{Introduction}
Computer-based laboratory examinations require infrastructure that is simultaneously reliable on commodity classroom hardware, observable enough for academic integrity enforcement, and resilient against transient network failures common in university lab environments. Commercial proctoring solutions are typically cloud-based, require continuous internet connectivity, and expose student data to third-party providers. Such trade-offs are often unacceptable in a controlled lab where the institution wants to retain full data custody and run the entire stack on a local area network.

This work describes a self-contained exam runtime that runs entirely on a single classroom LAN. One authoritative server process binds to a configurable host and port and announces itself via a UDP discovery beacon. Student clients locate the server either by an explicit host/port or by an automatic discovery exchange, authenticate against an allowed-user list and (optionally) an HMAC-signed token, and open a WebSocket runtime channel. During the exam, the client owns local observation--process snapshots, focused-window events, hardware deltas, idle detection, and screen replay--because only the student machine can produce that data. The server owns authoritative session state, policy distribution, and the submission archive.

The contributions of this paper are: (i) a layered architecture that cleanly separates the LAN runtime protocol from same-machine loopback IPC, preventing dashboard-control semantics from leaking into the student protocol; (ii) a normalized incident-rule engine shared by client and server that supports whitelist, warning, and blacklist classifications with operator-configurable actions; (iii) an authentication subsystem combining CATS preflight, Active Directory token validation, and a temporary-disable workflow gated by explicit admin approval--with passwords never persisted in the validation queue; (iv) a privacy-safe read-only projector view for in-room notification display; and (v) a documented testing strategy producing 151 automated tests across unit, integration, and system layers.

\section{System Architecture}\label{sec:arch}

\subsection{Process Topology}
The deployment consists of one server host running \texttt{server.main} and any number of student hosts running \texttt{client.main}. Each host may additionally spawn local UI processes: the server spawns a Tk or Qt operator dashboard, and the client spawns a Tk or Qt timer/submission window. Launchers (also Tk and Qt) supervise the CLI processes. Operators can also point a browser at \texttt{/projector} to display public-safe aggregate notifications in the classroom.

\subsection{Two Communication Planes}
The system intentionally exposes two distinct communication systems:

\begin{itemize}
  \item \textbf{LAN runtime plane:} JSON-over-HTTP for one-off operations (login, exam-config fetch, file download, submission upload, artifact upload, health check, auth-status query) and JSON-over-WebSocket for continuous exam runtime. This plane is bound to the configured server host/port and is the only channel between server and student.
  \item \textbf{Local IPC plane:} loopback-only WebSocket (\texttt{ws://127.0.0.1:<ephemeral>/ipc}) with a per-process random token, used between same-machine CLI/GUI/launcher processes. A stdio fallback is preserved for manual terminal operation.
\end{itemize}

This separation is enforced by binding the local IPC server only to \texttt{127.0.0.1}, validating loopback peers explicitly, and refusing tokens that do not match the per-process secret passed through environment variables.

\subsection{Package Responsibility Model}
The implementation is divided into four top-level Python packages:

\begin{itemize}
  \item \texttt{common/}: protocol envelope and checksum, event constructors, session security context, UDP discovery, loopback IPC, process and incident-rule definitions, text-safety helpers, and runtime logging.
  \item \texttt{server/}: HTTP and WebSocket handlers, persistent state, admin command parsing, time broadcast, GUI bridge, settings service, shutdown routine, and the projector endpoint.
  \item \texttt{client/}: discovery and login flow, exam preparation, WebSocket session, monitor orchestration, incident engine, incident buffer, transfer/upload pipeline, and the student-facing GUI bridge.
  \item \texttt{client/custommodules/}: process monitor, focused-window monitor, hardware monitor, idle monitor, replay recorder.
\end{itemize}

\section{Requirements Analysis}\label{sec:req}

\subsection{Functional Requirements (Summary)}
A complete Software Requirements Specification with stable requirement identifiers is provided as a separate companion document. The functional requirements are grouped as follows:

\begin{itemize}
  \item \textbf{FR-SRV-*} Server runtime: CLI argument validation, duplicate-server guard, route registration, persistent state, session state machine, time broadcast, admin commands, banned-user safety during global finish, WebSocket close-frame size compliance.
  \item \textbf{FR-CLI-*} Client runtime: discovery or direct connection, login, preflight, exam preparation, timer UI synchronization, monitor lifecycle across reconnect.
  \item \textbf{FR-MON-*} Monitoring: process snapshots and blacklist matching, focused-window with Unicode-normalized titles, idle detection with configurable thresholds, hardware deltas, screen replay with FFmpeg.
  \item \textbf{FR-INC-* / FR-POL-*} Incident rules and policy: normalized statuses (unknown / whitelist / warning / blacklist), priority resolution, server-side persistence, GUI decision flow.
  \item \textbf{FR-REC-*} Reconnect and buffering: durable incident queue with stable sequence numbers, deduplicated restore, evidence retry.
  \item \textbf{FR-SUB-*} Submission and artifact transfer: bundle build, manifest with per-file and archive SHA-256, multipart upload, server-side path safety.
  \item \textbf{FR-AUTH-*} Authentication: CATS and AD preflight, temporary disable with default 60-second TTL, operator-approved admin validation queue, HMAC token verification.
  \item \textbf{FR-IPC-* / FR-UI-*} Local IPC envelope and Tk/Qt GUI parity.
  \item \textbf{FR-PROJ-*} Projector page and SSE feed with public-safe payload by construction.
\end{itemize}

\subsection{Non-Functional Requirements (Summary)}
Non-functional requirements cover security (loopback-only local IPC, signed and optionally encrypted sensitive LAN events, HMAC token, safe ZIP extraction, upload size limits), privacy (no personally identifying or evidentiary data on the projector), reliability (reconnect treated as a network condition rather than a logging shutdown; persistent state normalization on load), observability (per-monitor JSONL logs plus per-process stdout/stderr capture), usability (Tk/Qt dashboard parity and stable list-refresh behaviour), and operability (rebuildable from \texttt{requirements.txt} with no external services).

\section{Design and Implementation}\label{sec:impl}

\subsection{LAN Runtime Protocol}
All WebSocket messages share the envelope \texttt{\{event, data, checksum\}} where the checksum is SHA-256 over the canonical JSON serialization of \texttt{event} and \texttt{data}. Malformed envelopes are rejected with a sentinel decode error. Sensitive events--\texttt{exam\_policy}, \texttt{policy\_update}, \texttt{session\_state}, \texttt{incident\_report}, \texttt{kill\_process}, \texttt{pause\_exam}, \texttt{resume\_exam}--are additionally wrapped by a session security context that signs the envelope with HMAC over canonical fields, includes a timestamp and nonce, optionally encrypts the payload with Fernet, and enforces a replay window.

\subsection{Server Subsystems}
The server uses \texttt{aiohttp} for HTTP, WebSocket, and SSE. The application factory \texttt{server.app.create\_app} registers ten routes (\texttt{/health}, \texttt{/auth/status}, \texttt{/login}, \texttt{/exam/config}, \texttt{/exam/files}, \texttt{/exam/submission}, \texttt{/client/artifact}, \texttt{/projector}, \texttt{/projector/events}, \texttt{/ws}) and starts background tasks for time broadcast, console reader, discovery announcer, and duplicate-server guard. Persistent user state lives in \texttt{data/server/users.json}; policy, blacklist, definitions, and incident-rules live in companion JSON files under the same folder.

The server-side session state machine resolves a live status (\texttt{waiting}, \texttt{exam\_started}, \texttt{paused}, \texttt{awaiting\_submission}, \texttt{finished}, \texttt{banned}, \texttt{kicked}, \texttt{disconnected}) from raw user fields and provides a single mutation entry point that keeps legacy boolean flags in sync. Admin commands are parsed by \texttt{server.tasks.handle\_admin\_command} and shared by stdin and GUI dispatch so the CLI and dashboard cannot diverge.

\subsection{Client Subsystems}
The client orchestration entry point is \texttt{client.ws\_client.WebSocketSession}, which owns the WebSocket connection, the timer GUI bridge, the stdin bridge, the incident engine, the incident buffer, the replay save queue, and four monitors (process, focused-window, hardware, idle). Crucially, monitors are not stopped on transient WebSocket disconnects; they continue to log to local JSONL files, and unsent incidents accumulate in a durable buffer that flushes in order after reconnect.

\subsection{Incident Rule Engine}
Incident rules are normalized JSON definitions matched against incidents using process-name, browser-process-name, and window-title patterns (with \texttt{contains} or \texttt{exact} mode). A best-match resolver chooses among matching rules by priority. Whitelist matches suppress the incident before warning or blacklist evaluation; warning and blacklist matches attach \texttt{matched\_incident\_rule}, \texttt{matched\_incident\_rule\_id}, and \texttt{configured\_actions} to the outgoing report, allowing the server to apply ban / kick / pause / kill-pid actions where context permits.

\section{Security and Privacy}\label{sec:sec}
The threat model assumes the LAN is trusted but student machines may be uncooperative. Controls layered against this model include: allowed-user gating; HMAC token validation; optional CATS and AD preflight; temporary-disable workflow that requires explicit operator approval and stores no passwords; checksum on every LAN message; signed and optionally encrypted sensitive events with timestamp, nonce, and replay window; loopback-only token-protected local IPC; safe ZIP extraction with manifest-tracked managed folders; configurable upload size limits and SHA-256 verification on uploads; and a public-safe projector payload constructed to exclude login identifiers, UUIDs, IP addresses, process names, window titles, paths, or evidence references.

\section{Testing and Validation}\label{sec:test}
Validation combines automated tests with a manual smoke checklist. The automated suite contains 29 unit tests, four integration tests, and two system tests for a total of 151 tests. The most recent run reported 149 passing tests; the two failures are isolated to Windows-path mock fixtures in \texttt{test\_replay\_recorder} and do not affect production code paths.

Critical regression areas explicitly covered by tests include:

\begin{itemize}
  \item \texttt{/finishexam} must not clear the banned flag on banned users.
  \item WebSocket close reasons must respect the 125-byte control-frame limit without splitting UTF-8 sequences.
  \item Secured error responses on malformed \texttt{process\_catch} events must remain wrapped in the session security context.
  \item Reconnect must not stop local monitoring or replay.
  \item The buffered-incident restore path must deduplicate by sequence identity.
  \item Exam ZIP extraction must not delete unmarked user folders on the desktop.
  \item Auth disable must expire on schedule and must require admin validation before login proceeds.
  \item Projector payload must remain free of personally identifying or evidentiary data.
\end{itemize}

\textbf{Critical bug fixes (10 May 2026).} Barış discovered, fixed, and regression-tested three production bugs on the \texttt{baris} git branch immediately before the integration milestone. (i) In \texttt{tasks.py \_handle\_finish\_exam\_global}, a global finish was inadvertently clearing the \texttt{banned} flag on banned users via the legacy-flag sync helper; the fix guards the loop with \texttt{if user.get("banned") or session\_state.derive\_state(user) == BANNED: continue}, and the new regression test \texttt{test\_finish\_exam\_global\_skips\_banned\_user} prevents recurrence. (iii) In \texttt{\_handle\_process\_catch\_event}, error responses for malformed events were sent through a raw \texttt{ws.send\_str} call while an active session security context existed, causing the client to fail decoding; the fix wraps the error envelope with \texttt{\_protect\_payload(client\_id, \dots)} so it respects the active security boundary. Cumulatively these fixes raised the automated test pass rate from 116 of 118 to 149 of 151.

\section{Conclusion and Future Work}\label{sec:conclusion}
This paper presented a complete LAN-resident exam runtime system covering authentication, exam lifecycle, multi-dimensional monitoring, incident classification, durable buffering, secure submission, and a public-safe projector view. The architecture deliberately separates the student-facing LAN protocol from same-machine loopback IPC, which keeps administrative semantics out of the protocol exposed to student hosts. The implementation has been validated through 151 automated tests and a documented manual smoke checklist; the remaining mock-related test failures will be addressed in the final delivery.

Future extensions include stronger authentication integration with centralized identity providers, signed settings bundles with policy provenance tracking, more precise browser observation through controlled extensions or accessibility APIs, an automated Windows packaging pipeline, and optional encrypted-at-rest storage for submissions and artifacts. A dedicated operator audit-log export format and per-course/per-exam profile management are also natural next steps.
